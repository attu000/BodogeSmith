# BodogeSmith

**任意の自作カードゲームを設計・共有・プレイできる、ブラウザ上の汎用カードテーブル**

ゲームデザイナーがブラウザ上で「カード置き場（フィールド）」と「カード」を設計し、複数人でリアルタイムにプレイできる Web アプリケーションです。UNO・トランプ・オリジナルカードゲームなど、任意のカードゲームをこのアプリ上で再現して遊べる環境を目指しています。

![ゲームプレイ画面](docs/images/1.png)
![ゲームデザイン編集画面](docs/images/2.png)

> **開発状況:** プロトタイプ段階です。基本的な「設計 → 部屋作成 → カード移動」は動作しますが、未実装・不完全な機能があります。詳しくは [現状の課題](#現状の課題) を参照してください。

## 作成背景

WebSocket 通信を取り入れたアプリを作ってみたい、と思ったのがきっかけです。あわせて、以前トランプカードゲームを自作していたときに「これを誰かと共有できないか」と考えていたことを思い出し、制作に踏み切りました。

当初は自作のトランプゲームそのもの（初期は UNO）を作ろうとしました。しかし、それでは作り方がある程度分かっていて自分にとっての新規性がありません。そこで、スクラッチのようなカードゲーム自体を作れる環境を用意する方針に切り替えました。

学習目的で作っているのでAIエージェントはほとんど使っていません。技術の学習と設計・開発を同時並行で進め、試行錯誤を繰り返しているため、良くも悪くも癖の強いコードになっています。

## コンセプト

### ルールは判定しない「仮想テーブル」

BodogeSmith はゲームのルールをプログラムで判定しません。サーバーが管理するのは次の 2 点だけです。

- **どこに、どのカードが、何番目にあるか**
- **そのカードが、誰から表・裏どちらに見えるか**

ルールを守るのはプレイヤー自身で、実物のテーブルでカードを動かすのと同じ感覚で遊びます。ルールをコードに落とさないことで、任意のカードゲームを同じ仕組みで扱えるようにしています。

### 各プレイヤーのスマートフォンが「自分の手元」

各プレイヤーの画面は一人称視点で構成されます。自分の手札は手前に表向きで、他のプレイヤーの手札は裏向きで表示されます。

## 遊び方

### 1. ゲームを設計する（ゲームデザイナー）

1. ログイン後、「ゲームを作成」からゲームデザイン編集画面に入る
2. フィールドの種類を追加する（Public / Personal。詳細は後述）
3. 各フィールドに表示枠を追加し、座標・サイズ・表示枚数・初期の表裏を設定する
4. カードを登録し、各カードの初期配置（どの Public フィールドに置くか）を指定する
5. 「公開」にすると、部屋でゲームとして選択できるようになる

### 2. 部屋を作ってゲームを始める

1. ホームから「部屋を作成」し、パスワードを設定する
2. 他のプレイヤーに部屋名とパスワードを伝えて参加してもらう
3. 全員が集まったら、部屋のオーナーが「部屋を締め切る」。全員がプレイ画面へ移動する
4. オーナー（ゲームマスター）がゲームを選択すると、ゲームが開始する

### 3. プレイ

- カードをドラッグ＆ドロップしてフィールド間を移動する
- 操作は WebSocket で部屋の全員にリアルタイムで反映される

## 設計方針

### 1. 設計図（GameDesign）と実体（Game）の分離

```
GameDesign（設計図） ──GameFactory がコピー──▶ Game（実際のゲーム）
```

ゲーム開始時に、`GameFactory` が `GameDesign` の内容を `Game` にコピーします。進行中のゲームは設計図を参照しないため、遊んでいる最中に設計図を編集してもゲームには影響しません。同じ設計図から複数の部屋で同時にゲームを作ることもできます。

### 2. フィールドの 2 分類と 3 階層

フィールドは次の 3 階層で定義します。

```
カテゴリ（Public / Personal）
└── フィールドの種類（例: 山札、手札）  ← カードが実際に入る場所
    └── 表示枠（仮想フィールド）        ← 画面上での見せ方
```

| カテゴリ | 意味 | カードリスト | UNO での例 |
|---|---|---|---|
| Public | 全員で共有する場所 | 1 つ | 山札（裏向き）、捨て札（表向き） |
| Personal | プレイヤーごとに持つ場所 | 人数分 | 手札 |

Personal フィールドには、誰の分を表示するかを表す `target_player` を設定します。たとえば「手札」という 1 つの種類に対して、次の 2 つの表示枠を作ります。

| 表示枠 | `target_player` | 表示 |
|---|---|---|
| 自分の手札 | `myself = true` | 画面手前に表向き |
| 相手の手札 | `others = true` | 画面奥に裏向き |

### 3. 一人称視点での設計

デザイナーは「自分が画面手前に座っている」視点だけでフィールドを配置します。プレイ時には、`myself` の表示枠にはそのプレイヤー自身の手札が、`others` の表示枠には他プレイヤーの手札が入ります。これにより、全員の画面がそれぞれの一人称視点になります。

### 4. 状態を 3 つの JSON に分離

`Game` は状態を責務ごとに 3 つの JSONField に分けて保持します（編集の容易さからJSON形式で保存していますが、本来はデータベース上でのより適切な保存方法を模索するべきだと考えています。。。）。

| フィールド | 役割 | 共通 / ユーザー別 |
|---|---|---|
| `_field_card_design_dict` | 各表示枠の見た目（座標・サイズ・表示枚数・初期の表裏・`target_player`） | 全員共通 |
| `_field_cardInfo_dict` | どのフィールドに、どのカードが、どの順番であるか | 全員共通 |
| `_card_status_for_user_dict` | 各カードが、各ユーザーから表・裏どちらに見えるか | ユーザー別 |

「配置という事実」と「誰からどう見えるか」を分けることで、同じ盤面を人によって違う見え方で扱えるようにしています。

### 5. サーバー側での情報の送り分け

カードを 1 枚動かしたときの処理の流れは次のとおりです。

```
[ブラウザ] ドラッグ＆ドロップ
   │  WebSocket: move_card
   ▼
[Game.move_card_fromAtoB]
   ├─ _field_cardInfo_dict を更新（カードを移動）
   └─ _card_status_for_user_dict を更新（移動先の設定から全員分の表裏を再計算）
   │
   ▼  部屋の全員へ「更新あり」を通知
[各接続の Consumer]
   └─ Game.create_fci_for_user_dict(自分の user_id)
        裏向きのカードは名前・画像 URL を空にして送信
   │
   ▼
[ブラウザ（Vue）] 受け取ったデータで再描画
```

表示用のデータはユーザーごとにサーバーで作るため、ブラウザの通信内容を見ても、裏向きのカードの名前や画像は含まれません。

### 6. Pydantic による JSONField の型チェック

Django の `JSONField` は任意の辞書を受け入れるため、構造が崩れても実行時まで気づけません。そこで、読み書きの際に Pydantic モデルを経由させ、次のような検証を行う方針にしています。

- Public と Personal でフィールド名が重複していないか
- 配置情報のフィールドが、デザインのフィールド定義と一致しているか
- ゲーム内の全カードが、重複なく、過不足なく配置されているか

```
DB (JSONField) ⇄ Python dict ⇄ Pydantic Model（構造の検証）
```

### 7. 操作ログによる巻き戻し（設計中）

カード操作を `{関数名, 引数, 実行ユーザー, 説明文, 日時}` の形でログに残し、直近の操作を逆向きに実行して状態を戻す設計です。シャッフルは乱数を使わない決まった並べ替えにしており、逆方向に実行すると元の順番に戻せるようにしています。

## 現状の課題

主要なものに絞って記載します。

### 未完成の機能

| 機能 | 状況 |
|---|---|
| シャッフル | 旧データ構造の名前が残っており、現状は動作しない |
| 巻き戻し（Undo） | ログの読み書きが動作しない。カード移動がログに記録されていない |
| 疑似シャッフルの逆変換 | 枚数が奇数のとき、逆方向に実行しても元の順番に戻らない |
| スマートフォン向け画面 | 現在読み込まれているのは PC 向けの画面のみ |
| 自動テスト | 未整備 |

### 設計上の課題

| 課題 | 内容 |
|---|---|
| 操作の権限チェック | サーバー側で「そのプレイヤーが操作してよいカード・場所か」を検証していない |
| 同時操作 | 状態を JSON ごと読み書きしており、排他制御がないため、同時に操作すると一方の変更が失われる可能性がある |
| 裏向きカードの秘匿 | 裏向きでもカード ID は送信しているため、ID と中身の対応を覚えると推測できる。シャッフルも決まった並べ替えのため順番を予測できる |
| Public フィールドの表示枠 | 現状は 1 種類につき表示枠 1 つを前提にした実装になっている |
| 通信量 | 1 枚動かすたびに、変化しないデザイン情報も含めて全員へ再送している |

### 本番運用に向けた課題

| 課題 | 内容 |
|---|---|
| Channel Layer | `InMemoryChannelLayer` を使用しており、複数プロセスでは動作しない（Redis 等への移行が必要） |
| 画像の保存先 | ローカルのファイルシステムに保存しており、Heroku では再起動で消える（S3 等の外部ストレージが必要） |

## データベース設計

```
GameDesign（設計図）
├── _name                      : str（一意）
├── _creater                   : FK → User
├── _published                 : bool
├── _player_limit              : int
├── _cards                     : M2M → Card
├── _field_card_design_dict    : JSONField  フィールドの見た目・設定
└── _init_field_cardInfo_dict  : JSONField  カードの初期配置

Game（実際のゲーム）
├── _name                      : str
├── _game_design_id            : int        元の設計図（リスタート用）
├── _players                   : M2M → User
├── _player_id_order           : JSONField  プレイヤーの並び順
├── _cards                     : M2M → Card
├── _field_card_design_dict    : JSONField  設計図からのコピー
├── _field_cardInfo_dict       : JSONField  現在のカード配置
├── _card_status_for_user_dict : JSONField  ユーザー別の表裏
└── _game_log                  : JSONField  操作履歴

Card
├── _name                      : str
└── _card_image                : ImageField

Room
├── _name                      : str（一意）
├── _password                  : str（ハッシュ化）
├── _owner                     : FK → User
├── _status                    : OPEN / CLOSED
├── _game                      : FK → Game
└── _playing_members           : M2M → User
```
